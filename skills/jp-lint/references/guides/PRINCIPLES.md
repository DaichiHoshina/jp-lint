## 最優先 — 読み手の認知負荷を下げる

ドキュメントは記憶ダンプではなく、判断や行動を助ける道具として機能する。すべてのルールはこの目的から派生する。

- 1回読めば理解できる文章を目指す
- 読み手に「で、つまり何？」と思わせない
- 「賢そう」でなく「伝わる」を優先する
- 初見の人が途中で止まらないこと

迷ったらこの4つに戻る。判断の優先順は「ルール準拠」より「読み手の負荷」。

## 文章生成の不変条件

文章の種類にかかわらず、次の条件を文体ルールや採点より優先する。

- 書き直し前後で、事実・時制・因果関係・主体・書き手の評価を変えない
- 入力や確認済み資料にない数値・事例・理由・感情を作らない。不明なものは「未確認」「未測定」と書くか省く
- 件数を記載する場合は、対象集合の要素を実物から列挙して件数と一致させる。似た集合や包含関係を同じ件数として扱わない
- 検証結果の断定は確認した主張の範囲に限る。build や test の成功だけで、文書内の事実をすべて確認したことにしない
- 文長・段落長・語尾・体言止め比率・採点は確認箇所を探す目安に留め、数値を合わせる目的で書き換えない
- **短くする目的で語を削らない** (user 指摘 2026-08-28: 短縮しようとして不自然な文になる)。主語・目的語・助詞・接続詞を削った文、動詞を名詞に変えた文、2 つの内容を 1 文に入れた文は、短くても読めない。文が長いと感じたら、語を削るのでなく意味の切れ目で 2 文に分ける。長くなった文をそのまま維持するのは正常で、字数を理由に戻さない
- 感謝、謝罪、感嘆符、絵文字を定型として強制しない。内容と宛先に必要なものだけ使う
- 箇条書き・見出し・改行は、並列する事実や手順があれば積極的に使う。散文の段落に含めず、視覚的に走査しやすい形に分ける。因果関係・判断理由・経緯など順序立てて追う内容は、これまで通り文章で書く。PREP は短文向けの構成として必要な場合に使う
- user が文体の説明を求めていない限り、適用した規則・採点・書き直し工程を本文や完了報告に出さない
- 読みやすさを理由に変更するのは、読み違い、判断の阻害、論理の断絶が起きる箇所に限る。意味が伝わる単語の類義語置換など、好みだけで分かれる変更は行わない。再点検のたびに新しい変更を作らない。例外は [NG-DICTIONARY.md](../NG-DICTIONARY.md) への語の追加で、追加した語は既存箇所も全件へ適用する (user 決定 2026-09-09、手順は `references/on-demand-rules/ng-word-register.md` Step 6)。辞書は好みでなく user 指摘を根拠に増えるので、再点検で新しい判断ができることはない
- 作業の完了報告は、読み手の判断に必要な要点だけを記載する。作業工程の列挙 (「〜を具体化した」「〜を明記した」等)、個々の言い換え、触らなかった箇所、成功した build / lint の詳細、今後の改善案、成果物本文を読めば分かる詳細の再掲は、user が求めた場合を除いて含めない。失敗や未解決の問題は省かない
- 今日の commit・NG 辞書・comment 規範を文章生成のたびに自動注入しない。`CLAUDE_WRITING_CONTEXT_INJECTION=1` は注入処理自体の検証時だけ使う

## 出力する言語 (日本語が基本)

説明のための文章は原則日本語で書く。対象はコードコメント / PR 本文 / GitHub issue / Design Doc / commit message / レビューコメント / chat 応答のすべてで、書くたびに言語を切り替えず一貫させる。英語にするのは下の例外に当たるときだけで、迷ったら日本語を採用する。

- **例外 1 — 周囲が英語**: 同じ file や同じ dir のコメントが英語でそろっているなら、そちらに合わせる。1 箇所だけ日本語を差し込むと表記が割れて読みにくくなる
- **例外 2 — 公開 OSS**: 外部の開発者が読む前提の repo は、その repo の慣習に従う
- **例外 3 — 読み手が日本語話者でない**: 宛先に日本語を読まない人がいる PR / issue は英語で書く
- 既存の英語コメントを、この原則を理由に日本語へ書き換えない (「文章生成の不変条件」 の「既存文書の一括置換をしない」と同じ扱い)
- **識別子は英語のままでよい** (user 指摘 2026-08-25): カラム名 / method 名 / 関数名 / 型名 / 定数名 / command 名など、コード上の名前を指す語は綴りそのまま書く。この原則が適用されるのは説明の地の文であって、名前の表記ではない

日本語の中で英語のまま維持する語の線引きは [「自然な話し言葉の日本語」](#自然な話し言葉の日本語-英語の混在抑制) が canonical とする。何語で書くか (本 section) と、どの語を英語で維持するか (同 section) を同時に使わない。

## plain JP の文体 (chat と人に宛てる text は敬体 / 外向き文書は常体)

chat も外向き text も **plain JP (開いた文章)** で書く。隣の席の同僚に説明するときの語り口で書き、飾り・前置き・締めの挨拶を付けない。助詞を省かず、意味が自然に完結する文で書く。

**chat 応答は敬体 (です・ます) で書く** (user 指示 2026-08-28: 短縮したような口調を全部なくしてほしい)。語尾を「〜です」「〜ます」「〜しました」「〜できます」で閉じ、「〜する」「〜した」の常体終止や「〜だ」の断定で閉じない。bullet の中も同じで、名詞句や動詞の終止形で切らず、敬体の文として完結させる。「済」「要確認」「対応中」のような省略語で状態を表さず、「対応しました」「確認が必要です」と文で書く。文を短くする目的で主語・目的語・助詞を省かない。同じ文末は 3 文続けず、3 文目に来たら文をまとめるか下位 bullet に下げる (canonical: 「(3) 文体より意味を優先する」)。

**人に宛てて書く text は敬体 (です・ます) で書く** (user 指示 2026-10-02: 他の人に向けるものは敬語にしてほしい)。対象は issue / PR のコメント、review の指摘と返信、Slack / Notion のメッセージで、chat 応答と同じく文末を敬体で閉じる。ただし chat と違い、文末に句点「。」は付けない。句点を付ける位置で改行し、1 行に 1 文を置く。先頭に `[memo]` `[nits]` `[must]` のようなラベルを付けるときは、ラベルだけを 1 行目に置き、本文は改行して 2 行目から書く (user 指示 2026-10-02)。

外向き文書 (PR body / issue の本文 / commit / code comment / design doc / local-docs / memory) は常体を基調とし、文末を特定の形に固定しない。ただし文末「〜だ」では閉じない (user 指摘 2026-08-03: 断定調の連発が浮いて読みづらい。2026-09-12 に句点の有無を問わず block する検査へ接続した)。動詞終止 (〜する / 〜した / 〜ある) や「〜になる」「〜として扱う」等で閉じる。名詞述語は「〜が対象になる」「〜を指す」のように動詞へ開く。検査は構造判定で行い、文末が「だ」で終わり直前が「ん」でない文を数える (撥音便の過去形「読んだ」は対象外にする)。**文体より意味の正確さを優先する**。表現を変化させる目的で、元の文にある受益・後悔・継続などの意味を加減しない。既存表現を語尾の文字列だけで置換しない。主体が曖昧になる箇所だけ主語を明示し、指示語は必要に応じて具体名に展開する。

外向き text (PR body / issue / commit / code comment / design doc / local-docs / memory / review の指摘と返信 / Slack / Notion) では文末に句点「。」を付けない (user 指示 2026-09-07、2026-10-02 に local-docs / memory / review を明記)。外向き text は箇条書きを基本形とし、1 bullet に 1 文だけを置く。句点で区切りたくなる 2 文目は同じ bullet に続けず、改行して下位 bullet (インデント) に分ける。段落の地の文でも 1 文 1 行にし、句点で文をつながない。chat 応答は敬体で句点を付けたままとする。code comment の同じ規則は code-comment.md 「文末の句点「。」は付けない」 にある

出力する text に字数基準の折り返しを入れない (user 指摘 2026-08-18)。1 文は 1 行に収め、改行は段落や論点の切れ目にだけ置く。表示幅は読み手の環境と貼り先が決めるもので、書き手が入れた改行は記載された先で不自然な段差になる。長い文は折り返さず、意味の切れ目で文を分ける。例外は commit message 本文で、git の慣習に従って折り返してよい。

### 自然な話し言葉の日本語 (英語の混在抑制)

chat 応答と外向き text では、日本語に訳しても指す対象が曖昧にならない一般語を日本語で書く。英語のまま維持するのは code 識別子 / command 名 / 固有名詞 / 和訳すると通じにくい定着済み開発用語 (commit / PR / hook / lint / API 等) に限る。config file の英語の混在する圧縮文体が chat に現れると翻訳調になり、読み手には不自然に映る。

- 置き換え例: file → ファイル / user → ユーザー / task → 作業 / repo → リポジトリ / dir → ディレクトリ / branch → ブランチ (文脈で迷ったら日本語側を採用する)
- **一般名詞の英語連結も開く** (user 指摘 2026-08-19): 「error 判別」「rollback は〜」のように英語名詞を地の文へ連結しない。カナで定着した語 (エラー / ロールバック / タイムアウト / リトライ / ロック / キャッシュ) はカナへ開く (「エラー種別の判定」「ロールバック処理は〜」)。識別子を指すときだけ綴りそのまま書く。同じ概念を英語とカナ / 和語で言い分けない (rollback と `巻き戻し` の混用等)。具体例の一覧: code-comment.md 「地の文の英語名詞」
- 英語直訳調の言い回しも開く: 「〜することができる」→「〜できる」/「〜を行う」→「〜する」/「〜が存在する」→「〜がある」
- **訳語は 1 語対応で決めない** (user 指摘 2026-08-29): 英語 1 語を日本語 1 語へ一律に置き換えない。採用した訳語が元の語の意味を過不足なく表すか確かめ、表せない語は使わずに事実を書き下す。「orphan process → 孤児」「time window → 窓」が典型で、訳語だけが残存して元の語の含意 (親を失った状態 / ある時間帯) が読み手に伝わらない。訳語が意味を表しきれないと感じたときに、修飾句を前へ追加して 1 語にまとめない。「親が死んだ孤児」は「孤児」が既に含む意味を繰り返しているだけで、「親プロセスが終了したのに残存しているプロセス」と文で書けば重複も曖昧さも消える
- **プロセスやジョブの状態を比喩や擬人化で書かない**: 「死んだ」「食われる」「腐る」のような比喩で状態を表さず、「終了した」「引数として解釈された」のように起きた動作をそのまま書く。この規範は chat 応答にも適用する。[NG-DICTIONARY.md](../NG-DICTIONARY.md) 「荒い比喩語」 の `skill-only` は hook で自動 block しないという意味であって、規範の適用先を外向き doc に限る意味ではない。code comment 側の具体例は code-comment.md 「擬人化 NG パターン」 にある
- 適用は新規に執筆する文の語彙選択に限る。既存文書の一括置換や、意味が伝わっている語の言い換えだけの再編集はしない (「文章生成の不変条件」)
- 対象外: CLAUDE.md / rules / 定義 file の圧縮文体、code block / YAML / command 名 / agent trailer

### chat 応答の基本形 (要点箇条書き default)

説明・報告・調査結果は、要点まで抽象化した箇条書きを default にする。地の文は導入 1 文と、因果を順に追って読ませたい説明だけに使う。

- 1 bullet は 1 論点とし、意味が完結する文で書く (名詞句のぶつ切り羅列にはしない)。文数や字数は目安で、収めるために語を削らない (「文章生成の不変条件」)。文末は敬体で閉じる (「plain JP の文体」)
- 抽象度は「読み手の次の判断に必要な要点」まで上げる。file path / 行番号 / 作業工程 / 成果物本文と重複する詳細は、user が求めた場合だけ出す
- 全体は要点を一目で走査できる適度な長さに保つ。ただし短くする目的で、失敗・未解決・破壊的影響を省かない

### 適用範囲

- chat 応答 (対話、思考過程、提案、報告)
- 外向き text (PR / commit / Issue / Slack / Notion / DD / PRD / RCA / comments)
- 考案フェーズ (`/plan` `/brainstorm` `/sdd-design` 等) の本文ドラフト

### 外向き文書の抽象度

目的は、読み手が見やすくなることだ。文字数を減らすことは目的にしない。抽象化とは、識別子を業務の言葉に置き換え、文として完結した日本語で説明することを指す。説明の文を削って短くすることは抽象化ではない (user 確定 2026-10-02)。

- 対象: PR body / issue コメント / review の指摘と返信 / code comment / local-docs / memory / エビデンス
  - code comment は、書くか書かないかを code-comment.md で決め、書くと決めた comment の抽象度にこの節を適用する
  - commit message は commit-message.md の「WHAT の重複を省く」に従う
- 手本: 「27cm のインハウスコードが変更されています」「27.5cm を無効にしています」
- 短くしすぎた NG: 「NOT NULL 化」「NULL 行を削除」のような名詞止めの断片。「発送依頼 ID が空のサイズ選択は保存できないようにする」のように、何が起きるかを文で書く
- 判定: 書き換える前と比べて 1 項目の文が短くなっただけなら、抽象化でなく短縮になっている。識別子が業務の言葉に置き換わったかで判定する
- 書かない: diff や対象 file を読めば分かること (関数名 / 型 / SQL の条件 / file path / test code の中身)
- 粒度: 読み手の次の判断に使わない作業の細部は書かない。変更した file の件数の内訳、触った箇所の一覧、作業の順序がこれにあたる。件数は判断に使うときだけ合計で書く (2026-10-02 の試験で、memory と local-docs の draft が識別子を含まないまま「テストデータ 9 ファイル、テストコード 4 ファイル」のような内訳を含めた)
- 例外: 読み手が判断に使う技術的な根拠 (lock の挙動、DDL の指定など) は削らず、見出しの下へ分けて書く。PR body での分け方は [pr-description.md 「抽象度の線引き」](pr-description.md#抽象度の線引き) に従う
CLAUDE.md / rules / config file の圧縮文体 (体言止め・英語の混在) は AI 向け設定記法であり、chat / 外向き出力の文体手本にしない。

### 閉じてない文章の禁止

閉じてない文章 (体言止めの連発・羅列・助詞省略・名詞ぶつ切り・動詞省略・主語省略の連発・英語名詞の助詞なし連結・表だけで完結) を全 context で禁止する。体言止めは、その形が情報を最も正確に表す場合に用いる。文末リズムや比率を整える目的では増減しない。

**code comment 内の日本語本文も対象** (`//` `/*` `--` `<!-- -->` `#` の後)。書くと決めた comment は常体を基調にする。体言止めの回数は script 判定せず、意味が完結しない羅列になっている場合だけ修正する。分量上限 / 書く・書かないの判定は code-comment.md が canonical。

### 冗長の禁止

- 聞かれていないことへの補足展開をしない
- 同じ内容の言い換え反復をしない
- 好みレベルの言い換えは行わない (詳細は上の「文章生成の不変条件」)

### 「完了」「〜済」の禁止

turn 締めを「完了」「〜完了」「〜済」で終えない。事実を先に書き、末尾も事実で締める。

- NG: 「baseline を更新した。push 完了。」
- OK: 「baseline を更新して push した。」
- 「〜済」も同じ理由で default 禁止する (事実だけ書けば伝わる)

送信前は、書き換えによって事実・時制・因果関係・主体・評価が変わっていないかを確かめる。読みにくさが残存する箇所だけ修正し、文長や文末などの指標を合わせるためには書き換えない。

### 模範ペア (3 つの欠点を同時に修正する例)

- NG: 「実装完了。hook が digest inject する構成へ refactor 済。なお念のため sync も実行済です。加えて、この変更により保守性が大幅に向上します。」
- OK: 「hook が要約を差し込む構成に書き換えて、sync まで実行した。」

## 文書全体の読みやすさ

文や単語を修正する前に、見出しと各段落の主張だけを追い、文書全体で次を確認する。読み手が目的、比較、結論、現在の状態、用語、因果関係を一意に読み取れない場合は、局所的な言い換えではなく構成を修正する。

**適用順序**: 執筆時は見出し設計 (outline) → 本文。見直しのときは skeleton pass (見出し — 役割 — 所有する主張) → 局所修正。どちらの経路でも、下の各項目を局所的な言い換えより先に適用する。

1. **読む目的を 1 つにする**: 調査記録、意思決定、実装手順など、読む目的や読後の行動が変わる内容は文書を分ける。読み手の目的は「学ぶ (入門) / 作業を終える (手順) / 調べる (仕様・一覧) / 理解する (仕組みと理由)」の 4 つで見分け、主目的以外の内容は付録か別の文書に分ける。報告書の「事実 / 解釈 / 提案」のように、1 つの報告目的を支える役割分担は混在に含めない
2. **結論の置き場所を 1 つにする**: 結論と理由を所有する section を決める。概要は結論を探す入口に留め、別 section の説明を言い換えて繰り返さない。詳細を読んだ後に判断を更新する PREP / SDS の再掲は、追加情報がある場合だけ配置する
3. **同じ問いへの選択肢を比べる**: decision の候補は同じ決定対象に答える形へ合わせる。複数の独立した判断を 1 案へまとめず、判断ごとに分ける。適用できない比較軸は、理由を添えた `N/A` として扱える
4. **現在の状態を記載する**: 完成稿には現在の事実と判断を記載し、執筆中の訂正や調査順序を含めない。ADR の不採用理由、RCA の時系列、判断に必要な前提変更は履歴ではなく証拠なので記載する
5. **同じ対象を同じ用語で呼ぶ**: 同じ指示対象を意図なく言い換えない。似た語が別の状態や対象を表す場合は、冒頭で違いを定義して使い分ける
6. **因果を順に読み取れる形にする**: 主体、条件、原因、結果の対応が一度で読み取れない箇所だけ、文や段落を分ける。因果が複雑であること自体を理由に分割せず、向きや参照先が曖昧な箇所を修正する
7. **見出しの階層を統一する**: 同じ役割の見出し (章どうし、節どうし) は同じ階層にし、途中の階層を省かない (H1 の直下に H3 を置かない)。番号付きの見出しは「1. 題」のように、番号の後に半角 space を置く形に統一する。Markdown の file での順序は `rules/markdown.md` の Structure と同じ
8. **見出し・図・表だけで大部分が分かる形にする**: 必要な章だけを読む読み手がいる前提で、見出しは話題の名前でなく節の主張にする (「守る指針」の 4)。情報の種類ごとに形式を決める。流れと構造は図、選択肢や役割の比較は表、手順と優先順位は番号付きリスト、理由と設計判断は文章にする
9. **強調は結論と守る条件だけにする**: 太字や注意の枠を多くの文に付けると、どれが重要か分からなくなる。1 つの章で強調する箇所は、結論か、読み手が守る条件に限る
10. **設計判断には理由を添える**: 採用した内容だけでなく、なぜそうしたかを記載する。複数の案を比べて決めた判断なら、採用しなかった案と、得たものと失ったもの (トレードオフ) も 1〜2 行で記載する
11. **後から参照される文書には鮮度を示す**: 共有して後から読まれる文書には、更新日と参照元 (関連する PR・仕様) を記載する。古い設計判断が現在の仕様と読み違えられるのを防ぐ

字数、文数、section 数、接続詞の数は、この確認の合否に使わない。問題が 1 文に閉じるなら局所修正し、複数 section に広がるなら重複の集約や文書分割まで行う。

### 専門語・翻訳調・カタい語を使わない (読み手知らない語禁止)

書き手が知ってる語 ≠ 読み手が知ってる語。中学生でも分かる日常和語を採用する。迷ったら短い和語。

- × 外挿 / 余裕大 / 無視可 / 無視可能 / 懸念解消 / 全観点 / 判定確定 / 漸近 / 線形 / 冪等性 / 直交 / ロバスト
- ○ 本番だと / 枠の半分以下 / 気にしなくていい / 心配なし / 全部OK / GOで進める

英語のまま維持するのは code 識別子 / command 名 / 固有名詞 / 定着済み開発用語 (commit / PR / hook / lint / API 等) に限り、破壊的操作の確認時のみ通常日本語に戻す。日本語で自然に言える一般語は日本語で書き、置換は PRINCIPLES-word-replace.md に従う。**書き手の語彙でなく読み手の語彙で書く**。本 section は外向き text だけでなく chat 応答にも適用する。意味が明確な用語を、日本語の類義語があるという理由だけで置き換えない。対象読者が意味を取れないか、文脈上の読み違いの原因になる場合だけ言い換える。

IT 用語を使ってよい範囲は、基本情報技術者試験で出題される程度とする。この範囲の用語 (テーブル、データベース、API など) は、読み手が非エンジニアでも「記録」「場所」のような曖昧な語に言い換えない。chat・外向き文書・memory・doc のすべてに適用する。

識別子 (テーブル名、関数名、file path など) を記載するのは、詳細設計 (`/sdd-phase-design`) の文書を基本とする。例外は 3 つで、Design Doc の Data Schema、根拠として示す `path:line`、code review で指摘する場所に限る。それ以外では識別子を使わず、上の範囲の IT 用語で説明する。

書く前の self-check: 「この語、user が知らないと言ったら言い換えられるか？」答え No なら使わない。

## 図は Mermaid で描く

作図は Mermaid を基本とする。doc も GitHub issue も PR 本文も同じ扱いで、構成図・流れ図・状態遷移・順序図は Mermaid の記法 (`flowchart` / `sequenceDiagram` / `stateDiagram-v2` / `erDiagram`) から採用する。text のまま diff に残り、GitHub の markdown でそのまま描画されるので、後から修正するときに元 file を探さずに済む。

- markdown では ```` ```mermaid ```` の code fence を使う
- ASCII の罫線図は使わない。等幅でない環境では桁がそろわず読みにくくなり、書き換えの手間も大きい
- 画像を添付するのは、実画面の screenshot や Mermaid で表せない図版に限る。そのときは画像にした理由を 1 行添える
- transaction の境界をまたぐ順序の説明は `sequenceDiagram` で描く
- 箱の label は読み手が観測する結果（誰が何を見るか）で書く。method 名と SQL は図の下の箇条書きへ出す
- 読めない図を修正するときは箱を増やして実装形を足さない。場面 1 つを中心にした図に差し替える

構文の注意点と DesignDoc での型の固定は [design-doc-protocol.md](design-doc-protocol.md) 「図表の型を固定する」 / 「Mermaid 構文の注意点」 が canonical となる。

## 見直し5観点

`/jp-lint` の見直しで使う観点の正本。structure gate（「文書全体の読みやすさ」）のあと、局所確認に進むときに適用する。

```
[A] readability: 読み違え、判断の阻害、論理の断絶の原因になる箇所だけを修正する / 段落は論点の境界で分ける / 必要な箇所だけ主語を明示 / 語順・読点位置・一文一義・主語述語の距離 (読みやすさ観点)。意味が伝わる単語の類義語置換など、好みレベルの変更は行わない
[B] visibility: heading hierarchy / bullet use / tables for types
[C] signal: PREP or TL;DR+detail / conclusion first
[D] evidence: 主張を入力内の数値・事例・根拠で支える / 根拠がなければ新しく作らない
[E] coherence: term consistency / no duplication / 文脈上不自然な鋳型反復・翻訳調を避ける / 文末反復や単語の一致だけを理由に言い換えない
```

5 軸は見落としを探す観点として使う。合計点や各軸の点数で合否を決めず、意味・事実・宛先・必須形式に関わる問題を修正する。同じ文書の再点検でも、変更を最低 1 件作る必要はない。短文投稿前の日本語ラベル対応は external-post.md 「最終チェック」。

## 初読者基準 — 初めて読む人でも分かる文章

読み手は「この会話・この repo・この PR を初めて見る人」と想定して書く。書き手が経過で得た文脈 (略称・固有名詞・前提知識) は読み手の頭にない。この節は分散していた基準の統合先で、chat 応答にも外向き text にも適用する。

### 媒体に合わせた読みやすさ

| 出力先 | 語彙と文の判断 | 詳細 |
|---|---|---|
| chat 応答 / 技術 doc (PR / DD / RCA) | 正確さを保ち、条件・因果・主語を読み違える所で文を分ける | この file 冒頭「専門語禁止」 |
| web 向け文書 (blog / 社外公開) | 見出しと段落の冒頭だけでも要点を読み取れるようにする | `## Web 可読性` |
| UI コピー / 通知文 | その場で必要な事象と次の操作だけを記載する | `### UI コピー / エラーメッセージ向け追加規約` |

どの媒体でも、字数を合否や分割の条件にしない。

### 用語は初出で開く (集約 pointer)

1. **難語・専門用語**: 削除でなく初出で 1 文の定義を併記する (`## AI臭を消す4変換` の (c)。例: 「idempotency (同リクエストを 2 回呼び出しても結果不変)」)
2. **内部 jargon**: 初出で和訳を添える (`### NG辞書` 直下の「内部jargon初出和訳必須」list)
3. **略語**: 初出でフル展開する (同「略語初出展開必須」list。例: RCA (Root Cause Analysis))
5. **公式 doc に無い言い回し**: 使う前に、その語が対象 product の公式 doc にあるかを確かめる。無ければ定義を添えても使わず、その語が指す役割を日本語で書く (例: `backing index` → 「外部キーの検査に利用される index」)。公式 doc の語なら項目 1 のとおり初出で定義を併記する。実際に指摘が発生した語は `NG-DICTIONARY.md` 「非公式専門用語 (block)」へ登録して hook の検査対象にする

### 前提知識を補う

- 会話の経過で作った略称・案番号 (「案A」「finding 3」「例の hook」) を最終出力に含めない。中身を書き下す
- 「なぜこの話をしているか」が本文だけで分かるようにする。背景が 1 文で書けるなら冒頭に置く
- 読み手が本文を理解するのに別 file / 別スレッドを開く必要がある構成にしない。判断に必要な要点は本文へ転記し、link は補助に使う

### 圧縮文を開く (括弧詰め込み / 主語なし識別子文)

書き手 memo の圧縮をそのまま用いると、初読者は文意を復元できない。負荷試験レポートの user 指摘「何言ってるかわからん」(2026-07-19) を再発源として基準化した。hook は「読点 2 個以上 + 動詞なしの括弧」を script で warn する (`_check_sentence_structure_counts` の括弧詰め込み検出)。

1. **括弧に名詞を 3 つ以上詰め込まない**。読点区切りの括弧内羅列は本文の文に開く。項目が対等に並ぶなら箇条書きに開く (条件は「箇条書き階層化」の「段落から箇条書きに開く条件」)。括弧は補足 1 要素までとする
2. **識別子で始まる主語なし文を含めない**。「`X` 固定とする」ではなく、何を `X` に固定するのかを主語 + 役割で記載する
3. **flag / 関数名は初出で役割を 1 句添える** (上記「用語は初出で開く」4 の identifier 適用)

- NG: 「`fetchViaCache` 固定とする (`legacy_mode` は不採用)。フラグは `Maintenance` のみ使う (admin API、503 化用途、DD 6-2 節)。」
- OK: 「読み込みは cache 経由の `fetchViaCache` だけを通し、旧経路に戻す `legacy_mode` フラグは使わない。運用フラグは `Maintenance` の 1 つだけにする。admin API から立てると API が 503 を返して処理を止められる (詳細は DD 6-2 節)。」

### 「状況 → 読み手の結果 → 対処」の順で書き、対処は具体的な動作で書く (全外向き文章)

分岐や制約を説明する文は、「状況 (いつ / どの入力で)」→「読み手に見える結果 (画面や呼び出し側に何が起きるか)」→「対処 (この変更やこの行が何をするか)」の順で 1 文に並べる。雛形は code comment の `hidden のときは画面がサイズ欄を出さないので、Label は空のまま返す` で、code comment だけでなく PR body の bullet / commit の Why / review 返信 / issue の背景にも同じ型を適用する (user 確定 2026-08-28)。分かりにくい文の主因は、主語が `UI` / `status` / `文言` のように抽象で、何が起きて何を空にするかを読み手が復元できないことだった。

- **状況は具体名で開く**: `このケース` `欠落` `決定的` `不整合時` のような書き手のラベルでなく、`hidden のとき` / `発送依頼済みなのにサイズを特定できないとき` / `map の反復順に依存すると` のように、code や diff を見なくても状況が分かる語で書く
- **結果は読み手側で書く**: 仕組みの説明 (「NULL になる」) で止めず、画面や呼び出し側に何が起きるか (「画面がサイズ欄を出さない」「発送担当者が別サイズを箱に入れる」) まで書く
- **対処は具体的な動作で書く**: `文言は設定しない` でなく「ラベルは空のまま返す」、`非表示に倒す` でなく「サイズ欄は表示しない」。読み手が見るものと、code が空にする項目や返す値を業務の言葉で対応させ、識別子は直下の行や diff で見えないときだけ backtick で添える (「外向き文書の抽象度」、2026-10-02 改訂)
- **口語の圧縮動詞を使わない**: `流す` `倒す` `詰める` `引く` `寄せる` `畳む` は、監視ログへ記録する / 表示しない / フィールドを空にする / 取得する / 1 か所にまとめる、のどれかを読み手が復元しなければならない。意味をそのまま動詞で書く
- **曖昧な汎用動詞を避ける**: `出す` `外す` `持つ` `見る` `入れる` `切る` のように意味の範囲が広く文脈依存になる動詞を使わず、実際の処理を表す具体的な動詞 (返す / 生成する / 削除する / 無効化する / 維持する / 検証する / 作成する / レビューする) を使う (canonical: NG-DICTIONARY.md 「曖昧な汎用動詞」)
- **1 文で理由と対処を閉じる**: 「なので」「ため」の前が状況と結果、後ろが対処。理由だけ、動作だけの文にしない
- **接続の助詞は対処の直前に 1 つだけ置く**: 前提 → 結果 → 対処 の 3 段があるとき、「前提なので結果し、対処」と書くと結果と対処が並列に読め、対処の理由が前提なのか結果なのか決まらない。「前提で結果のため、対処」のように、対処を導く助詞を対処の直前に置く (user 指摘 2026-09-11: 「定義だけを書き換える方式なので一瞬で終わり、lock の指定は書かない」→「定義だけを書き換える方式で一瞬で終わるため、lock の指定は書かない」)
- **対処を文頭に置かない**: 「条件 B も入れているのは、条件 A だけだと別の行まで結びつくからです」のように採った対処から書くと、その対処が無いときに何が起きるかが「ため」の中に埋まる。先にその失敗を書き、対処は「そのため」のあとに置く。「〜であることは X が担保する」も、名詞化した性質が主語になり、何が起きるかが残らない。code comment の同型は `code-comment.md` 「失敗を先に書き、対処は「そのため」のあと」
- **評価の枕詞で始めない**: 「通常は」「困難なので」「予防策として」「正とする」で始めると、読み手に何が起きるかが残らない。先にその状態で何が分からなくなるかを書く。同型は `code-comment.md` 「評価の枕詞で始めない」
- **指示語は同じ文か直前の 1 文だけを受ける**: 「これ」「それ」「この X」「上の〜」「5〜9 の手順」「3 行目」のような指示語を使ってよいのは、参照先が同じ文の中か、直前の 1 文にあるときだけにする。参照先との間に別の文・段落・表が入ったら、指示語を使わずに指している名詞にする。間に文が入ると、読み手は参照先を特定できない。直前の 1 文でも、主語と述語のどちらを指すか決まらないなら名詞を繰り返す。逆に、参照先が直前の文の主語に決まるのに同じ名詞を 3 文以上続けて繰り返すと、読み手が名詞の数だけ同一かを確かめることになるので、「この X」「その X」で受ける。同型は `code-comment.md` 「指示語は同じ文か直前の 1 文だけを受ける」
  - NG (表の後の段落で): 「特につらかったのは 3 行目です」「5〜9 の手順は、全部この状態に向かうためのものです」
  - OK: 「特につらかったのは、実装者より先にレビュワーが問題に気づくことでした」「Phase ごとに繰り返す詳細設計から説明までの手順は、全部『レビュー依頼のときに説明できる状態』に向かうためのものです」
- **先頭文を手段の列挙にしない**: 「A を追加し、B を削除して、C で担保する方式を提案する」のように、文書や節の先頭が手段の並びだと、読み手が困っていることが文に無い。先頭は困りごとと、そのとき何が分からなくなるかにする。手段は次の文に分ける
- **分類を主語にして動作を付けない**: 「不一致の case は確認が返す」のように、種類を主語にすると、動作する主体が入れ替わる。主語は確認や関数にし、種類は「〜のとき」に置く。同型は `code-comment.md` 「分類を主語にして動作を付けない」
- **「として」で役割を重ねない**: 型や入力を主語にしたまま「として」で役割を重ねると、誰が何をするかが消える。同型は `code-comment.md` 「「として」で役割を重ねない」
- **「扱い」で残すか消すかを隠さない**: 「対象外扱いにしない」は、残すのか消すのかが名詞の中に隠れる。残す対象と消す対象を分ける。同型は `code-comment.md` 「「扱い」で残すか消すかを隠さない」

媒体ごとの当て方:

| 媒体 | 型の当て方 | NG → OK |
|---|---|---|
| code comment | 該当行の真上に 1 文 (canonical: `code-comment.md` 「状況 → 読み手の結果 → コードの対処」) | `非表示 status では文言を空に倒す` → `hidden のときは画面がサイズ欄を出さないので、Label は空のまま返す` |
| PR body の変更 bullet | 上位 bullet = 対処 (変更 1 文)、下位 bullet = 状況 → 結果 | `- 不整合時の表示制御を追加` → `- 発送依頼済みなのにサイズを特定できない景品は、サイズ欄を空で返す` / `  - そのまま出すと発送担当者が別サイズの商品を箱に入れてしまうため` |
| commit の Why | 1 行目に状況 → 結果を書き、subject が対処 | `Why: 不整合対応` → `Why: 発送依頼済みでサイズを特定できない景品をそのまま表示すると、発送担当者が別サイズを箱に入れてしまう` |
| review 返信 | 1 文目で対処 (識別子付き)、2 文目で状況 → 結果 | `表示側で吸収した` → `hidden のときは \`Label\` を空で返すようにした (\`abc1234\`)。画面はサイズ欄を出さないので空でよい` |
| issue の背景 | 状況 → 結果を段落で書き、「やること」が対処 | `サイズ表示の不整合がある` → `発送依頼済みなのにサイズを特定できない景品があり、管理画面がそのまま表示すると発送担当者が別サイズを箱に入れてしまう` |

適用範囲は新規に執筆する文と、review や質問で意味を問われた文の書き直しに限る。指摘されていない既存文をこの型に合わせる目的で書き換えない。見出し・godoc の要約行・表の項目名は対象や名前そのものの説明なので、「〜のときは」型に無理に合わせない。

### 主張は目的と観測した事実の大きさで書く (外向き文章)

読み手は、書かれた主張をそのまま判断の材料にする。主張が書き手の内部事情に寄るか、事実より大きく書かれていると、読み手は自分の状況に当てはめられないか、事実と違う期待を抱く。

- 書き手の組織や個人に固有の数値・運用は、読み手が自分に当てはめられる一般的な言い方にする (「チームの目安は 200 行」ではなく「一般的にレビューしやすい行数を目安にする」)
- 仕組みや機能は、手段や数値の目標ではなく、何のためにするか (目的と効果) で書く (「指摘を 0 件にする」ではなく「指摘をレビュー依頼の前に解決しておく」)
- 効果は観測した変化の大きさで書く。「〜できるようになった」「〜が無くなった」と、変化を全か無かに言い切らない (「調べ直さずに返信できる」ではなく「調べ直す時間が短くなった」)
- 目標は、達成した状態として断定せず、目指すものとして書く (「〜になっている。これが理想です」ではなく「〜になっていることを目指します」)
- 読み手の判断や行動を変えない前置き (対象の範囲の注記、書き手の事情) は書かない
- 手順を表にするときは「順番 / やること / 手段 / 詳細」の列にし、「やること」は一言の名詞にする。読み手は「やること」の列だけを縦に読んで全体の流れをつかむ

適用範囲は、読み手が判断に使う外向き文章 (記事 / Design Doc / PR 本文 / 提案資料) とする。chat の報告は対象外。

### 1 文の述語に時点を 2 つ掛けない

1 文の述語に、時点や主体を 2 つ掛けない。時点が変わる境界（この PR とリリース後、消すものと残すもの）で文を分ける。読点でつなぐと、動詞がどちらの時点の行為なのかが決まらない。

- NG: 「前の変更の続き、最後の作業で、公開のあと不要な箇所を削除する。」
- OK: 「前の変更の続きで、この一連の最後の作業である。呼ばれなくなった経路は、この作業で撤去する。反映は、前の変更の公開から一定期間のあとである。」

適用範囲は新規に執筆する文と、意味を問われた文の書き直しに限る。指摘されていない既存文をこの型に合わせる目的で書き換えない。

### 談話構造 — 1 つの論点を段落内でつなぐ

段落の中心となる主張に、理解に必要な根拠や注意点をつなげる。論点が変わる所で段落を分けるが、文数や字数を合わせるためには分けない。すべての段落を同じ文数や「主張・根拠・補足」の固定構成にしない。

- NG: 「cache 層を追加した。TTL は 60 秒。invalidation は event 駆動。」(名詞の羅列で、なぜ・どう効果が生じるかが読めない)
- OK: 「一覧 API に cache 層を追加して応答を p99 1.2s から 320ms に縮めた。TTL は 60 秒にした。在庫更新のずれが心配になるが、更新 event で即時に cache を消すので古い値は最大でも数秒しか残存しない。」

文の単位でも同じ流れを守る。文の頭は既知情報 (直前の文を受ける語) にし、新情報は文の後半に置く (既知 → 新)。

- NG: 「cache を無効化した。TTL の設定値が原因だった問題は再発しなくなった。」(2 文目の頭が新情報で、前文とのつながりが切れる)
- OK: 「cache を無効化した。この無効化で、TTL 設定が原因だった問題は再発しなくなった。」

出典: 木下是雄『理科系の作文技術』(既知 → 新情報の連結)。

## 書く前の4問

抽象的な答え不可。答えずに執筆するとAI文体になる。

1. **読み手は具体的に誰か** (×「エンジニア」○「新joinのsenior backend」「レビュアーAyanoさん」)
2. **読後に何を決めさせる / やらせるか** (×「理解させる」○「approveを決めさせる」「migrationを実行させる」)
3. **主張を裏付ける確認済みの根拠** (数字・事例・code・log。無ければ作らず「未測定」とする)
4. **「なぜ？」と聞かれたら** (×「〜が必須」○「localStorageにtoken置かない、XSSで抜かれる」)

## chat 出力前 先手 sweep 5 pattern

chat / 外向き text の送信前に以下 5 pattern を目視で点検し、該当があれば送信前に修正する。jp-quality-block hook の warn を retry で消すより、先手で消した方が token cost が安い。

1. **意味を取りにくい漢語の連結**: 名詞の関係が分からない場合は助詞を挿入するか訓読みに開く。→ 「行の自動注入」「依頼を準備中」「固有名詞の系統」
2. **意味が欠けた bullet**: 名詞句だけでは対象・状態・関係が分からない場合は、必要な助詞や動詞を補う。名詞句で意味が確定する項目名や結果は、そのまま維持する
3. **読み違えの原因になる文**: 条件・因果・主語と述語の対応を一度で読み取れない場合だけ、意味の切れ目で分ける
4. **矢印チェーン**: `A → B → C` の矢印羅列を、動詞のある文章に展開する。→ 「A を B に変換して C へ渡す」
5. **数字コード bare 出現**: MySQL エラー番号 `1062` / HTTP `409` / errno 数字など、書き手だけが即座に意味を取れる数字を単独で記載しない。読み手が辞書なしで意味を取れる語に置き換える (「重複エラー」「重複による 409」)。記載する場合は「重複エラー (MySQL 1062)」のように意味を先に記載する

先手 sweep は「書くと決めた文」に対する check で、書くかどうかの判定は先に済ませる (「書く前の 4 問」)。詳細 grep は 「script 検出 grep」 参照。

## 守る指針 (9原則)

1. **用語を並べるだけで説明しない**: 専門用語の羅列は内容ゼロ。1用語ごとに「何のために・どう動くか」を1文添える
2. **暗黙知を前提にしない**: 「いつもの」「ご存知の通り」を使ったら、その内容を1文で書く
3. **次の疑問を先回り**: 1段落書いたら「読み手が次に何を聞きたいか」を想像し、次段落に答えを置く
4. **見出しだけで流れが分かる**: 見出しはラベル (「アーキテクチャ」) でなく主張 (「読み書きを分離して負荷を分散する」)
5. **段落に役割を割り当てる**: 各段落は「背景 / 理由 / 具体例 / 結論 / 注意点」のどれかに該当。役割が曖昧なら削除or分割
6. **抽象説明に根拠を添える**: 判断に必要なら、確認済みの仕組み・事例・コード・測定値を添える。説明のためだけに数値を作らない
7. **「賢そう」より「伝わる」**: 平易で短い文を採用する。読み手は実務判断のために読む
8. **現在の事実のみを書く (経過メモ禁止)**: 「当初 X だったが Y に変更」「レビュー指摘で修正」等の開発中・執筆中の変遷を本文に記載しない。変遷は git history / レビュースレッド / 版管理が記録する。不採用案が読み手の判断に必要な場合のみ「Y を採用した。X は〜のため不採用」と**現在形の採用理由**で 1-2 行記載する。適用先: PR body / commit / issue / Slack / DD / RCA / code comment / chat 報告の全て
9. **見出しと本文を実装と突き合わせて整合させる**: 抽象語を含む見出し (「sentinel error で定義する」「判定用エラー値として定義する」等) を記載する前に、実装 diff を読んで実際に何を返しているか確認する。本文だけ実態に合わせて見出しに間違った抽象語を用いると、見出しは本文より先に目に入るため読み手を誤誘導する。文字列 match で分類する wrap 関数なら「MySQL 1062 の重複エラーを UNIQUE 制約名で分類して `%w` wrap する」のように、実装が実際にやっていることで記載する

## chat 応答の識別子強調 (bold + backtick 併用)

chat 応答内で file path / 関数名 / 変数名 / shell command / key 名を初出や強調で示すときは、backtick 単独ではなく `**` + backtick 併用にする。

```
NG: `sync.sh` を実行する
OK: **`sync.sh`** を実行する
```

**Why**: chat の inline code (backtick 単独) は背景色が薄く、monospace だけでは地の文と区別がつかない。

**How to apply**:

- chat 応答で識別子を初出 or 強調したいときは `**` + backtick で囲む
- 日本語の説明文や一般語には bold を付けない (noise になる)
- 外向き prose (PR / commit / doc) は対象外、従来通り backtick 単独で十分

## markdown 長文 doc の 1 文 1 行 + 下位 bullet

DesignDoc / PRD / RCA など markdown 長文 doc は 1 文ごとに改行する。1 つの bullet を複数文に分けるときは、**2 文目以降を下位 bullet (`- ` を付けて 1 段深く) にする**。素のインデント改行 (bullet なしで空白だけ下げる) は禁止。

### OK

```markdown
- サイズ行の UPDATE は、次の 2 条件を両方満たすときのみ許可する。
  - 対象商品が非アクティブ、かつ未発送 0 件。
  - それ以外は 409。
```

### NG

```markdown
- サイズ行の UPDATE は、次の 2 条件を両方満たすときのみ許可する。
  対象商品が非アクティブ、かつ未発送 0 件。
  それ以外は 409。
```

**Why**: 素のインデント改行は「これは何の継続?」を読み手が推測する必要がある。下位 bullet 化で上位と下位の関係が視覚的に明確になる。

**How to apply**:

- 文を改行で割ったら、継続行の頭に `- ` を付けて 1 段ネストする
- 見出し直下の通常段落を複数文に割る場合も、`- ` bullet 化してから下位 bullet にする
- 既存の非 bullet 複数行段落は diff を広げないため触らない。新規 / 編集した箇所だけ合わせる

## ドラフト便宜名・過去経緯・自作造語の禁止

チーム共有文章 (DesignDoc / PR / issue / Slack) にドラフト中の便宜名 (「B-lite」「第 3 世代」「案 E」等) や自作造語を記載しない。

- **NG**: 「B-lite」「第 3 世代」「案 E」など自作ラベル、「当初は案 B で検討していたが〜」の過去経緯
- **OK**: 「新方式」「旧方式」「事前シャッフル方式」など実装名 / 汎用用語で書く。比較は Alternatives 節に並列表で並べる

**How to apply**:

- 投稿・commit 前に本文を grep し、自作便宜名・「当初は」「以前は」を検出したら書き換える
- 難語・英語略語は初出で日本語補足を付ける (例: 「段階移行 (Parallel Change: 追加 → 移行 → 削除)」)
- 事実未確認の前提 (「既存に flag がある / ○○が存在」等) は `grep` / `find_symbol` / `gh pr view` で裏取りしてから書く

## 状態変化に合わせて section 名を更新する

docs section は **現状を表す名前** にする。状態が変わったら section 名 / 表 column 名も更新する。

例 (架空):
- 試験前: 「未決事項」表 (status: in_progress 列あり)
- 試験完了後: 「検証結果」に rename、status 列削除 (完了で進捗 enum 不要)
- 仕様確定後: 「仕様」に rename、判断経緯は別 section に記載する

**判断**: section 名が現状とずれした瞬間に rename + cross-ref 更新。「未決事項」のまま中身が確定値の表になっていると読者が混乱する。

rename に伴い他 file / 同 file 内 cross-ref も `[未決事項 #X]` → `[検証結果 #X]` のように全置換する。

2. 理由: 現象 / 影響 / 原因

- 並列する事実・手順・比較項目は箇条書きで書き、因果・判断理由は段落で書く。表・コードブロックは内容に適した場合だけ使う

## 結論・理由・根拠をつなぐ

判断を促す文章では、結論と、その判断に必要な理由・根拠をつなぐ。PREP は選択肢の 1 つであり、文章の長さだけを理由に固定構造を強制しない。作業完了報告では、成果と必要な検証だけを返し、作業工程を水増ししない。
### 構造

- **P**oint (結論): 一行で何が起きたか / 何を変えたか
- **R**eason (理由): なぜそれが必要だったか (incident / 不便 / 目標)
- **E**xample (具体例): how の詳細、数値、動作、file path
- **P**oint (再確認): 締めの一行、効果や次の手

P/R/E/P の label は、それが読み手の判断を助ける場合だけ使う。短い応答や単純な完了報告には付けない。

### 5W1H チェック

| 観点 | 充足例 | 欠落時の症状 |
|---|---|---|
| What | 「`/review` を 2 段階に変更」 | 「強化した」だけで何かわからない |
| **Why** (必須) | 「subagent 任せで見落とし発生」 | 「読み手が判断不能」「で?」と返される |
| **How** (必須) | 「parent が 7 観点で再 check、全 mode 適用」 | 抽象論で再現性なし |
| When/Where | commit hash / 日付 / file path | 通常 hash で足りる |
| Who | (省略可、necessary 時のみ) | 通常 commit author で足りる |

### 禁止 / 推奨

- **抽象語禁止**: 軸 / 層 / 経路 / 狙い / 方針 → 業務の事実か、起きた現象に置換する (file path や識別子を加える意味ではない。「外向き文書の抽象度」)
- **段落は 1 つの話題に限定する**: 話題が変わる箇所で分ける。並列する事実は箇条書きへ分けてよいが、行数だけを理由に因果・判断理由の段落を箇条書きへ変えない
- **接続文削減**: 「背景は〜」「〜の延長線上にある」など本題と関係ない補足は削る
- **文末の基調は常体**: 外向き文書は常体で書く。人に宛てる text (コメント / review / Slack) は敬体で書く (「plain JP の文体」)。意味に合う文末を選び、体言止めは情報を正確に表す場合に使う
- **文体より意味を優先**: 文末の反復を消すためだけの言い換えをしない。「〜できた」は達成、「〜している」は継続、「〜となった」は変化、「〜する方針」は判断を加えるため、元の文にない意味なら使わない。反復が読みにくい場合は関連する文をまとめるか、重複する事実を削る。ただし同じ文末が 3 文続く形は避ける

### 例 (commit まとめ)

```text
**結論**: `/review` を 2 段階 self-check に変えた。
**理由**: 1 段階だと subagent 任せで見落としや過剰指摘が残存する。
**例**: parent が 7 観点で再 check。全 mode 適用。file: `commands/review.md`
**結論再確認**: subagent 単独判定の見落としを parent が見つけられる状態。
```

10 行未満の応答は label を付けず、同じ順序を地の文で書く。

```text
`/review` を 2 段階 self-check に変えた。1 段階だと subagent 任せで見落としが残存するためで、parent が 7 観点で再 check する。file: `commands/review.md`
```

### decision 要求時の Point 変種 (decision-frame-first)

応答が user に decision を求める場合、Point は調査結果でなく **決定の枠** を提示する。trigger は (1) 末尾が `?` で締める質問 (2) 本文に選択肢 (A/B、案 1/2、Yes/No、どちらにする、どう進める 等) を含む — 両方満たす応答全て、長さ閾値なし (短文 3 行でも適用)。

冒頭 1 行に `要決定: <選択肢の枠> / <候補数>` を置く。

```text
要決定: 子 project memory が parent を継承するか (Yes/No → 子削除可否)
情報: W2 完了 (16 file 削除)、統合方針は 1 通り、最終確認 1 点

要決定: 2 widget × 各 2 案 = 4 通り (A/B 独立、A から 1 つ採用する / B から 1 つ採用する)
情報: 両 widget とも attribute 不在で 0 件確定
```


## chatとdocumentで文体を分ける

| 場面 | 方針 |
|------|------|
| Chat応答 | 敬体の開いた文章 (この file「plain JP の文体」+「初読者基準」)、結論先出し、要点を省かない |
| ヒト向けdocument | 意味が完結する文、主語明示、地の文と箇条書き混在、文体は「plain JP の文体」の分け方に従う、事実・時制を維持 |

**document基本ルール**:

- 主語必須 (「担当者は〜」「ユーザーは〜」)
- 指示語は同じ文か直前の 1 文だけを受ける。間に文が入った参照 (「上記」「前述」「これ」) は具体名にする (「指示語は同じ文か直前の 1 文だけを受ける」)
- 略語禁止 (初出はフルスペル)
- 「適宜」「状況に応じて」禁止 → IF-THEN形式で明文化
- 日付YYYY-MM-DD、英数字半角

### chat 草稿 → 外向き翻訳の 8 観点 sweep

chat 草稿の圧縮 (名詞句の羅列・書き手のラベル) をそのまま外向き (PR / Slack / Notion / 報告) に流用しない。chat 自体も圧縮せず敬体の文で書くので、翻訳の主眼は文体と読み手の前提の違いになる。文体は、人に宛てる text (コメント / review / Slack) なら敬体のまま句点を外し、文書 (PR body / 報告 / Notion の記事) なら常体へ書き換える。
下書き完成後、以下 8 観点で sweep してから提示する。

1. **意味が欠けた名詞句の解消 (常体基調)**
   - NG: 「3.5-7 分で完了見込み」「余裕大」「全観点クリア」「追加リスクなし」
   - OK: 「3.5〜7 分で完了する見込みになる」「十分な余裕がある」「いずれの観点でも問題は発生しない」「追加のリスクはないと判断する」
2. **略記を具体数値・正式名称化** — 詳細は AI臭を消す4変換 (a) 参照
3. **難解漢語・jargon 排除** — 「外挿」「諸元」等 → 平易表現。漢語が連なって名詞同士の関係を読めない場合は助詞を補う (例: 「段階的強化」→「段階的に強化」、「逐次化検出」→「逐次に並ぶ状態を検出」)。固有名詞・技術用語は対象外
4. **指示語・矢印・記号 → 文展開**
   - NG: 間に文が入った「上記」「これ」「それ」、「→ 本番でも数秒〜10 秒」
   - OK: 「前項の設定値」「<具体名>」「〜のため、本番でも数秒から 10 秒程度で完了する」
5. **主語明示** — 「実走した」→「<実施者> が実走した」または「テストとして実走した」
6. **表のセル内も単位明示**
   - NG: `188K×1` / `9秒` / `mismatch=0`
   - OK: `188,000 行 × 1 件` / `9 秒` / `mismatch=0 件`
7. **曖昧名詞は範囲明示**
   - NG: 「テスト完了」「動作確認」
   - OK: 「inventory_batch と notification_service を本番想定手順で実行した」
8. **AI 定型語 / カタカナ造語の事前 sweep** — NG 辞書から grep

詳細運用は「[## script 検出 grep (出力前 sweep)](#script 検出-grep-出力前-sweep)」section と連動する。

### UI コピー / エラーメッセージ向け追加規約

ユーザー向け UI 表示文言・エラーメッセージは「やさしい日本語」基準を適用する。

- その場で必要な事象と次の操作を一度で理解できる長さにする。字数上限では判定しない
- 難読漢語を避け、小学校 4 年生程度の語彙を採用する
- 専門用語の代わりに具体動作を記載する (NG: `認証エラー` / OK: `ログインに失敗しました。パスワードを確認してください。`)
- 一文一意 (複文 / 並列禁止)

## 構造原則 (docs 観点)

- **散文より bullet ファースト**: 説明は bullet で書く、地の文は接続・背景・結論のみ
- 各セクション直下に **目的 1 行** を添える
- 強調太字は GO/NO-GO 基準等の **限定箇所のみ** (濫用で埋没)
- forward reference は **anchor link 化** (「○○参照」より `[○○](#xxx)`)
- 用語は **他参照で再定義しない** (用語ポインタ表に統一)
- **同一概念は同一用語で呼ぶ**: 意図なく言い換えない (「設定 file」「構成 file」「config」の揺れ禁止)。表現の変化より一義性を優先する (出典: 木下是雄 / SmartHR Design System)
- **概念を漢字 1 文字の比喩で言い換えない**: 「形」「木」「幹」「根」のような 1 文字は、何を指すかを読み手が復元できない。短い名詞を作らず、中身をそのまま書く (「形」1 文字で呼ばず「回答に、決められた見出しか末尾の行が無い」と書く。user 指示 2026-10-11)
- **タスク完了に必須の情報を補足・脚注に置かない**: 前提条件は手順より前に本文で書く。補足枠に入れてよいのは読まなくても支障がない情報だけ
- 環境・テストデータ等は **別 SoT 参照**、本書では再記しない

## 箇条書き階層化

外向き doc (DesignDoc / PRD / PR 本文 / レビュー結果) と chat 応答の箇条書きに共通で適用する。種別 file はこの節を参照し、種別固有の使い方だけを書き足す。

- 因果連鎖・所属関係・補足説明は **上位と下位の階層で表現** (平坦に並列禁止)、2 スペースインデント統一
- 同一階層に並列するのは **対等な並列のみ**
- **入れ子は 2 階層まで**。上位 = 結論 1 文、下位 = 理由と補足 (論点ごとに分けて同じ階層に並べる)。3 階層目が必要なら見出しに上げるか、段落へ戻す

### 段落から箇条書きに開く条件

段落の中に並列する項目が詰め込まれていれば、箇条書きか表に組み替える。次のどれかに当たれば組み替える。

- 1 文に並列する項目が 3 つ以上ある (「A、B、C など」「(A、B、C)」)
- 分類や選択肢を並べている (「X と Y に分類する」「X か Y か Z」)
- 順番に行う作業を 1 つの段落で説明している。この場合は番号付きの箇条書きにする
- 同じ形の文が 3 文以上続き、それぞれが別の事柄を述べている

組み替えるときは、箇条書きの前に、何の一覧かを示す 1 文を置く。理由や因果でつながった文は、箇条書きにせず段落のまま維持する。

### 書き方 (結論 → 理由 → 補足)

「結論 → 理由 → 補足」は内容の順番で、入れ子の深さではない。補足は理由の下に 3 階層目として置かず、理由と同じ下位の階層に並べる。

- **結論を先に記載する** (行頭 = 結論、根拠は下位)
- **下位に理由と補足を置く** (複数行可、2 スペースインデント)
- **bullet 内でも意味を完結させる**。項目名・結果・状態を表す名詞句は、無理に動詞文へ変えない
- **1 行で読めるなら分けない**
- 階層だけで関係を追いにくい複雑な内容は段落文に切り替える

### checkable pattern (書く前に script で sweep 可能)

平坦 bullet を書き切ってから、以下 3 pattern を目視で点検し、該当があれば上位と下位の階層に組み替える。

1. **同レベル bullet に異なる意味単位が混在する** → file / module / 変更種別 / 論点など、内容に合う単位でまとめる。項目数だけでは組み替えない。
2. **理由語 (「〜ので」「〜ため」「〜だから」「〜なので」) を含む bullet が同レベルに混在する** → 理由文は上位 bullet の下位に置く。例えば「A を追加する」「A を追加する理由は B のため」を並列に置かない。後者を前者の下位 bullet にする。
3. **`(` で始まる補足や PR 番号 / issue 番号を含む bullet が同レベルに並ぶ** → 補足は上位 bullet の末尾に `()` で括って統合するか、下位 bullet に置く。参照リンクだけの独立 bullet は作らない。
4. **1 つの bullet に 3 文以上、または結論のあとに理由文・補足文が続く** → 上位 bullet には結論 1 文 (+ commit / PR 番号の `()`) だけを残し、2 文目以降を下位 bullet に置く。理由と補足が別の論点なら下位 bullet も分ける。pattern 2 と 3 は bullet 間の検査で、この pattern は bullet 内の検査なので、平坦に見えても必ず両方を見る (2026-08-26 に共有文で指摘)。

### NG / OK 例 (階層で結論と根拠を分ける)

NG (平坦・結論と根拠が並列):

```markdown
- 親商品の識別子を writer で NULL にする
- has_variant=true のとき、親の items 側の識別子を NULL にする
- このルールを svc に置くと usecase ごとに同じ判定が必要になるので、writer に置く
```

OK (親 = 変更、子 = why / how):

  - svc 側に置くと usecase ごとに同じ判定を実装するため、writer に置いた。

NG (pattern 4、1 bullet に結論・理由・補足を入れる):

```markdown
- `formatSizeLabel` を削除し、呼び出し元へ処理を戻しました (f25c7856ae0)。この関数の実態は `undefined` を `null` に変換するだけでした。必要だった理由も、渡し先の props が省略できない `string | null` だったという一箇所の型の制約に限られます。保有中一覧では同じ値をすでに直接読んでいたため、交換済み側も呼び出し元で `?? null` と書き、helper と test を削除しました

OK (上位 = 結論 1 文、下位 = 理由と補足を論点ごとに分ける):

```markdown

  - 実態は `undefined` を `null` に変換するだけで、渡し先の props が `string | null` という一箇所の型の制約でしか必要ではありませんでした

## ミクロ規則

- 文は、条件・因果・主語と述語の対応を読み違える所で分ける
- 一文一義 (1 文に 1 つの内容) を基本にする。50〜70 字を超える文は読み違えの確認候補にする (字数を合わせる目的では書き換えない)
- 表記 (全角読点 / 数字と単位 / カタカナ長音 / 漢字とひらがなの使い分け) で迷ったら JTF 日本語標準スタイルガイドに従う。漢字が続いて画面が黒く見える所は、ひらがなに開いて余白を作る
- 助詞重複 (「のの」「をを」「がが」) 排除
- 絶対表現 (「必ず」「絶対に」「完全に」) は GO/NO-GO 基準での使用を推奨し、説明文では「〜するとよい」「〜が望ましい」など穏やかな表現に言い換えるとよい
- セクション記号 `§` は使わない (見出しは `## 3. API設計`、節は `Section 1` / `第1節`、他 file の参照は見出し名の引用で足りる)。hook が chat と外向き text の両方で block する (`NG-DICTIONARY.md` の「記号 (block)」、user 指示 2026-09-10)
- 「埋める」より「記録する」「測定値を記入する」 (docs 寄り)
- web 出力時は `## Web 可読性` の走査しやすさを追加で確認する

## Web 可読性 (scan 前提)

外向き prose は web (GitHub / GitLab / Notion / Slack / Confluence) で読まれる。読者は読まずに **scan する** (NNG: 79% scan / 16% line-by-line)。chat 応答と別の構造が必要になる。

### scan pattern 対応

| pattern | 読者行動 | 書き手の対応 |
|---|---|---|
| F-pattern | 上から左寄り、段落先頭数語のみ読む | 段落先頭に keyword、左端に情報 |
| layer-cake | 見出しだけ読んで必要箇所だけ本文へ | 見出しを「主張」化、descriptive に |
| spotted | 太字 / link / 数値だけ読む | keyword を太字、評価語に数値併記 |

外向き文書生成時 (`/git-push --pr` / `/post-comment`) は 3 pattern の **どれで読まれても主旨が伝わるか** を self-check する。

### Web 用 ミクロ規則

- **文のつながり** — 条件・因果・主語を読み取れない文だけ、意味の切れ目で分ける
- **段落のまとまり** — 同じ論点の理由や注意点はつなぎ、論点が変わる所で分ける
- **平易な表記** — 文脈に合えば「行う / 出来る / 事 / 物 / 為」を「やる / できる / こと / もの / ため」に開く
- **見出しは主張化** — 「アーキテクチャ」 NG / 「読み書き分離で負荷分散」 OK
- **結論先出し + 本文量半減** (inverted pyramid)
- **数値 / file path は太字 or `code`** — spotted pattern で拾われる確率上昇
- **見出し / キャッチは意味単位で改行** — Notion / Slack は実 viewer で preview
- **コードブロック / list の前後に空行** — renderer 差で潰れる対策
- **heading 前 2 語に keyword (front-loading)** — F-pattern で末尾は読まれない。先頭語が情報の核になるよう語順反転 (NG `データ可視化による不正検出の早期化` / OK `不正を 24% 早期検出: データ可視化導入`)
- **heading の文脈外自己完結** — search result / SNS feed / RSS で heading のみ露出するため、具体的事実 (数値 / 対象) を含める
- **heading は 1 メッセージに限定する** — 句読点を増やして複数論点を詰め込まない
- **a11y: 色 + 書体 / 文言の二重識別** — 強調はボールド + 色、必須項目は「赤字」でなく「赤い ※ のついた」、色弱者 / screen reader 利用者に渡る
- **WCAG 3.1.5 reading level**: 中学卒業相当 (連続ひらがな + 漢字長の計算式) を超えるなら平易版 or 要約ページを併記
- **モバイル: 難解語は読む速度を下げる** — comprehension は維持されるが読速低下で離脱する。SP 想定なら語数削減 + 平易語選択

### 出力前 web 用 追加 check (既存 7 項目に追加)

- [ ] 文の条件・因果・主語を一度で読み取れる
- [ ] 見出しが主張型 (ラベル型でない)
- [ ] 段落ごとに主張が 1 つで、論点の境目に空行がある
- [ ] keyword / 数値 / file path が太字 or `code` で scan 可能

1 文単位の品質 (修飾語の語順 / 同一助詞連続 / 受身の能動化 / ら抜き / 冗長圧縮 / 弱い表現禁止 / 逆接「が」/ `!?` 不使用 / 漢数字・桁区切り / 見出し常体 / 全角かっこ) は `references/writing-sentence-rules.md` へ分離した。深い書き直し / `/jp-lint` 実行時も文脈と意味の維持を優先する。文長などの script 測定は user が明示した場合だけ診断用に使う。

## AI臭の根本: 書き手不在

AI 臭の正体は表層の記号や常套句でなく **書き手の不在** にある。主語が誰でもなく、見出しに評価が滲み、段落の呼吸が一定で、読み手に渡したい結論が不明。記号を修正しても書き手が居なければ AI 臭は残存する。下記 4 軸で「自分が書いた痕跡」を本文に含める。語彙 NG (L3) と約物 (L5) は `NG-DICTIONARY.md` / `pre-tool-use.sh` がscript 検出するため本 section では扱わない。中黒の並列と装飾絵文字だけは正当用法と区別できず hook が判定できないので、(4) で目視の対象として維持する。

### (1) 主体を明示する (False agency 除去)

主体不明の総称断定 (「多くの〜」「一般に〜」「よく〜される」) は書き手不在の最頻形。主語を **特定の人 / PR / doc / system** に置き換え、根拠を 1 文添える。

| NG | OK |
|----|----|
| 多くのエンジニアが型定義に苦労する | 私はこの PR で型定義を 3 度書き換えた。原因は generic 越しの推論が ts 5.4 で変わったため |
| 一般に N+1 は避けるべきだ | 本 service は list API で N+1 を許容している。1 list 50 件 × 平均 200ms の余裕があり、preload 実装の保守コストを上回らない |
| よく挙げられるのは可読性の向上だ | 本 refactor は 1 PR で触る file 数を 5 以下に抑えることを目的とする。週次 review 時間が 90 分 → 45 分に減る |

### (2) 見出しを中立名詞句に降ろす

PRINCIPLES.md `## scan pattern 対応` で「見出しの主張化」を推奨するが、**主観形容詞 (重要 / 効率的 / 強力 / シンプル) が含まれる主張化** は AI 臭が出やすい書き方だ。事実 / 数値 / 対象を含む中立名詞句に降ろす。形容詞を入れるなら根拠を添える。

変換の具体例 (効率的な → 数値、強力な → 件数) は下の `## AI臭を消す4変換 → (a) 抽象語 → 数字 / 事例` の table と共通する。見出しに使う場合も同じ「抽象語 → 数字」変換を適用する。

### (3) 文体より意味を優先する

AI 出力は段落長や文末が均質になりやすいが、変化を付けること自体を目的にしない。文体調整の前後で、事実・時制・因果関係・書き手の評価を変えない。自然な変化は情報の単位を整えた結果として生まれる。

- 同じ文末を 3 文続けない (user 指示 2026-09-12: 「ます。ます。ます。」のような連続が読みづらい)。2 文までは、並列した事実を最も正確に表すなら維持する
  - 検査は構造判定で行う (`_check_sentence_structure_counts` の同一文末 3 連続検出)。chat は block、外向き file は warn とする。読み手に見える並びで同じ文末が 3 文続けば検出し、bullet の階層・行の区切り・見出し・空行では切らない。表・引用・code fence で切る (user 指示 2026-10-07: 見た目で続いたら検出する。それまでは bullet 列を行ごとに、見出しと空行の位置でも切っていた)
- 3 文目に同じ文末が来たら、語尾の文字列を差し替えるのではなく構成を変える。関連する 2 文を 1 文にまとめる、2 文目以降を下位 bullet に下げる、重複する事実を削る、の順で修正する
- 読みにくい場合は、関連する文をまとめる、重複を削る、段落を分ける、の順で修正する
- 表現を変化させる目的で、受益・後悔・継続などの意味を加減しない。既存表現を語尾の文字列だけで置換しない
- 体言止めは情報を正確に表せる箇所だけに使う。回数や文末の変化を作る目的では増減しない
- user が文体そのものを尋ねていない限り、規則の適用過程を本文や作業報告で説明しない

意味の変化は文末の文字列からscript 検出できない。`/jp-lint` では書き換え前後の事実・時制・評価を比較する。

### (4) 構造テンプレから外れる

書き手が居ても、AI が好む型をそのまま使うと不自然に見える。下記 4 つは語彙 NG と違って grep で script 検出できないため、書き終わりに目で見る。出典は [stop-ai-slop-jp](https://github.com/iKora128/stop-ai-slop-jp) (MIT) で、この repo の適用範囲に合わせて書き換えた。

**a. 3 項目並列を疑う**。「3 つのポイント」「3 つの観点」は、3 つ目が 1 つ目と 2 つ目の言い換えになりやすい。2 つか 1 つに削れないか確かめてから採用する。数を先に決めて中身を埋めない。

**b. 二項対比を直接 Y に変える**。「A ではなく B だ」「単なる A ではなく B だ」は、A に言及する必然がなければ「B だ」と直接書く。A が読み手の実際の誤解であるときだけ対比を用いる。

| NG | OK |
|----|----|
| これは単なる lint 追加ではなく、review 負荷の設計だ | 週次 review の 90 分のうち 40 分が形式指摘だった。lint に任せてその分を消す |
| 速度ではなく正確さを優先した | 正確さを優先した。誤検出 1 件の手戻りが 30 分で、実行時間 3 秒の短縮より重い |

**c. 中黒の 3 項目並列を開く**。地の文で読ませる並列 (`ログとメトリクスとトレースを見る`) を `ログ・メトリクス・トレース` と圧縮しない。読点か「と」「や」で開く。表、見出し、箇条書きの中の圧縮表記は対象外。

**d. 装飾絵文字を等間隔に撒かない**。段落末や見出し先頭への 🚀🎯✨💡 の均等配置は AI 出力の代表的な特徴。判定を示す記号 (`external-post.md` の ⚠️ / ✅ を表の評価列に使う等) は情報を含むので対象外。

## AI臭を消す4変換

### (a) 抽象語 → 確認済みの数字 / 事例

入力や調査結果に根拠が無ければ数字や事例を作らない。評価語を削るか、「未測定」「仮説」と明示する。

| NG | OK |
|----|----|
| レスポンス速度を大幅改善 | p99 1.2s → 320ms (-73%)。Redis cache + N+1削除 |
| エラー処理を強化 | 5xx日次120件 → 8件。`context.WithTimeout` を全handlerに追加 |
| 効率的に作成可能 | md直接投稿できる。手動コピペ廃止が目的 |

### (b) 評価語 → 根拠1文併記

「適切な / 最適な / 改善 / 重要 / 必須 / 推奨 / 一般的に / 強化 / 向上 / 活用」を記載するなら**直後に1文で根拠** (なぜ・事例・数字)。

| NG | OK |
|----|----|
| セッショントークンの適切な管理が必須 | session tokenはcookie `httpOnly` に。localStorageはXSS経由で盗まれ、tokenにexpiryしかないため全アカウント乗っ取り可 |

### (c) 難語 → 削除でなく定義併記

初出で1文の定義を併記。専門用語を削ると正確さを失う。

| NG | OK |
|----|----|
| idempotencyを担保 | idempotency (同リクエストを2回呼び出しても結果不変) を担保。retryで二重注文発生しない |
| CQRSで整合性 | CQRS (読み書きを別モデル分離) で整合性。readはreplicaから返せてscale可 |

### (d) 英単語 → 日本語の平易表現

詳細置換表: `PRINCIPLES-word-replace.md` 参照。

### NG辞書

hook が動的抽出する NG 語 list は **[NG-DICTIONARY.md](../NG-DICTIONARY.md)** に集約。key 名 / 記法は 1 文字も変えない。NG-DICTIONARY 掲載語の訳語は同 file の置換例を正とし、この file 側で別訳を作らない。

**内部jargon初出和訳必須**: taigen-dome (体言止め) / canonical (正) / inject (差し込む) / scope (範囲) / fallback (代替) / boundary (境界)

**略語初出展開必須**: DoD (Definition of Done) / RCA (Root Cause Analysis) / PRD (Product Requirements Document) / DD (Design Doc) / SPOF (Single Point of Failure) / ROI (Return on Investment) / MVP (Minimum Viable Product) / WTP (Willingness to Pay) / MECE (Mutually Exclusive, Collectively Exhaustive)

**硬い文語**: 読み手や媒体に対して過度に硬い場合だけ、意味と断定の強さを保って平易にする。語尾の文字列を禁止語として一律に置換しない

## 避けるパターン (段落・文章全体の構造)

| パターン | 症状 | 対処 |
|----------|------|------|
| 抽象的なポエム | 名詞だけで構成、絵が浮かばない | 具体的な状況・行動・数値に置換 |
| 用語の羅列 | 専門用語が並ぶが各々の関係が不明 | 関係を1文で繋ぐか、1つに限定する |
| 過剰に丁寧な表現 | 「いただきますよう〜」「〜していただければ〜」 | 直接的な動詞文に短縮 |
| 余分な形容詞 | 「強力な」「革新的な」「柔軟な」が情報を含まない | 削除or数値 / 事例に置換 |
| 同義反復 | 同じ内容を言い換えて繰り返す | 1箇所に集約 |
| 中身のないまとめ | 「以上をまとめると重要だ」で何も結論してない | 1文の結論を記載するか、まとめ自体を削除 |
| PR 文脈依存の表現 | 「DD の X-Y 節を参照」「incident (YYYY-MM-DD) で観測」等、半年〜1年後の読者に通じない社内文書参照・日付 | 必要情報は本文に書き起こし、社内URL・過去日付は削除する |
| 時限的マーカー (merge 後意味喪失) | 「この PR で新設」「この commit で削除」「先週合意した通り」「上述の通り」「直近の incident で」等、merge / 投稿後の読者に通じない時限文言 | 削除 or timeless 表現に置換 (「実装初期」「初版」等は OK)、状態完了マーカー (「対策反映済み」) は timeless として維持する |
| 同 file 内 section 重複 (議論ポイント表 / 監視 / 採用理由 等) | 同論点が複数 section に分散、片方が要約 / 片方が詳細でも内容重複 | 詳細 section を残し、要約側は anchor link 1 行に圧縮。即統合できない場合は併存維持で別 task 化 |
| 複合名詞スタック | タイトル / 見出しで複合名詞を 3 個以上連結し、動詞・助詞が無い | 複合名詞は 2 個まで。3 個以上は動詞文に変換する |
| 自己物語導入 | 「本日のセッションで〜」「あわせて〜」等、書き手の作業経緯から書き始める | 読み手の判断に必要な事実から書き始める |

## 出力前セルフチェック

```
[ ] 読み手が必要とする結論を、本題と無関係な前置きより先に示した
[ ] 「必須」「推奨」「重要」に 1 文の根拠併記
[ ] 初出専門用語に定義併記
[ ] 抽象語 (改善 / 最適化 / 効率化) に、判断に必要な確認済みの根拠を添えた
[ ] 読み手の次アクション (approve / 実行 / 質問) が末尾明示
[ ] `## 書く前の4問` (L27) の 4 問に答えてる
[ ] 文書の読む目的と読後の行動が 1 つに定まっている
[ ] 結論と理由の所有 section が 1 つで、他 section に同義反復がない
[ ] decision の選択肢が同じ問いに答え、独立した判断を 1 案にまとめていない
[ ] 経過メモゼロ (「当初は」「以前は」「〜に変更した」「レビュー指摘で」を grep、現在の事実のみ)
[ ] 同じ指示対象を同じ用語で呼び、別概念との違いが読める
[ ] 主体・条件・原因・結果を順に読み取れる
[ ] 箇条書きの項目間に、並列・上位下位・因果のどの関係があるか読み取れる
```

該当する項目を確認し、内容上の欠陥があれば修正してから出力する。項目数による合否判定はしない。
web 出力時は `## Web 可読性` の追加 check 4 項目も適用。

## script 検出 grep (出力前 sweep)

通常の執筆・見直しでは本文を通読し、script 検出を完了条件にしない。user が文体指標の測定を明示した場合だけ、`scripts/jp-textlint.sh <file>` を診断用に実行できる。測定値や finding 件数は、依頼された場合を除いて本文や完了報告へ出さない。

### 基本 grep (略記・記号・jargon)

```bash
grep -nE '(M 行|K 行|→|外挿|諸元|逐次伝播|long TX|replica lag|disk I/O)' <draft>
```

### NG 辞書由来 grep (AI 定型語 / カタカナ造語禁止)

NG 語 canonical: [NG-DICTIONARY.md](../NG-DICTIONARY.md)。全 key (AI定型語 / カタカナ造語禁止 / 難読漢語 / 弱い表現 / 冗長表現 / 非日常英語) の literal はそちら参照。hit したら該当行を書き換えてから出力する。

## 全体マップ — 各ルールがどう認知負荷を下げるか

ルールは「読み手が払うはずだった負荷を書き手が肩代わりする」ためにある。形だけのルール準拠はAI調に戻る。

| ルール | 認知負荷をどう下げるか |
|--------|---------------------|
| 4問 | 「誰のためか」を最初に限定し、読み手が自分事として読める |
| 媒体別構造 | 形が決まっていれば読み手は内容に集中できる |
| 文体分離 | documentは常体・主語必須・離れた指示語なし → 読み返し不要 |
| 4変換 | 抽象語の解釈労力を書き手が引き受ける |
| 守る指針 | 段落ごとに役割を割り当て、見出しだけで流れが伝わる |
| セルフチェック | 文体の乱れを script で検出、見落としを救う |

迷ったら「各ルールは読み手の負荷をどう下げるか」を自問する。答えられないルール適用は形だけになる。
