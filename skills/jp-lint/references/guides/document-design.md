# 文書作成の共通規則 (章立て・書き直し・図)

<!-- writing-tree: parent=PRINCIPLES.md role=content -->
<!-- writing-tree-required: 1. 手法・仕組みの紹介文書の章立て | 2. 既存の文書を書き直すときの規則 -->

人が読む文書を作る・書き直すときに、媒体 (Notion のページ / HTML の Artifact / local-docs の HTML / md / 記事) によらず従う規則。媒体ごとの見た目と書き込みの手順は、媒体の skill (`notion-writing` / `local-docs` / `tech-article` など) が扱う。文と語の規則は `PRINCIPLES.md`、長文の種別ごとの規則は `long-form-doc.md` にある。

## 1. 手法・仕組みの紹介文書の章立て

手法や仕組みを紹介する文書 (Notion のページ / HTML の Artifact / 記事) は、媒体によらず次の順で章を構成する。読み手は「読むかどうか」を先に決め、細部は使うときに読むので、判断に必要な情報を前に、細部を後ろに置く。

| 順 | 章 | 中身 | 読み手の問い |
|---|---|---|---|
| 1 | 冒頭 | 目的と、この手法に固有の特徴を 2〜4 文。直後に工程の図 (線路図) | 全体として何をするか |
| 2 | 概要 | 方針の要点と、変更の規模ごとに使うかどうかの表 | 自分の作業で使うべきか |
| 3 | 理由 | 課題と対応の表。課題は実際に困った事実で書く | なぜこの進め方か |
| 4 | 一般的な手法との違い | 比較の表 | 既存の手法と何が違うか |
| 5 | 仕組みの要点 | 3〜5 項目。文書・コマンドの役割の表はここに置く | どう動くか |
| 6 | 用語 / 付録 | 用語の定義 (折りたたみ)、コマンドの一覧など本文から参照されない詳細 | 細部を調べたい |

違いを仕組みより前に置くのは、独自の部分を知ってから細部を読めるようにするため。

図は依頼が無くても描く。書き終えた章ごとに、次のどれかを文だけで説明していないかを確かめ、当たれば `artifact-diagramming` skill を読んで SVG を手描きする。

- 工程や処理の流れ (どの順に何が渡るか)
- 判定と分岐 (条件を満たさないとどこへ戻るか)
- 時間の経過 (最初に 1 回 / Phase ごとに繰り返す など)
- 2 つの案や手法の違い (どの矢印が増える・消えるか)

文 1〜2 行で伝わる内容や、比較の表で足りる内容には描かない。図の中の文字は短い名詞句にし、説明の文は図の前後の地の文に記載する。

見出しの文は、話題の名前 (「PR について」) ではなく、その節の主張 (「PR はレビューのしやすさを優先して分ける」) にする (`PRINCIPLES.md` 「文書全体の読みやすさ」の 8)。

- 工程の図 (線路図) は冒頭の文の直後に置き、補足に回さない。読み手は流れを知ってから課題や仕組みを読む
- 手法に固有の特徴 (他の手法に無い工程など) は、冒頭の文で 1 度紹介する。後半の章で初めて登場させない
- 本文の理解に必要な説明 (図に含まれる文書の意味、独自の工程の中身など) は付録やトグルに移さず本文に置く
- 各章の頭には、前の章とつなぐ 1 文 (「1 章の 3 つの課題に対して〜」) を置く
- 1 つの事柄は 1 つの章だけが説明する。全体の流れの章が役割を説明した文書やコマンドは、特徴の章では工夫した点だけを記載し、役割を言い換えて繰り返さない。課題と対応の表の「対応」列は 1 行程度にとどめる
- 課題が抽象的で、読み手が自分の作業に当てはめにくいときだけ、具体例の章を置く。架空でよいので 1 つの機能を題材にし、各文書に何を記載するかを表で並べる。題材は書き手に確かめ、実在の未公開情報は記載しない。課題が実体験の言葉で書かれていれば、具体例の章は置かない
- 具体例の表の各行は、前の行と範囲を一致させる。前の文書で決めた範囲の外まで、後の文書の例が及ばないようにする。条件や基準の例には、読み手が判定できる中身 (何をもって条件を満たすか) まで含める
- 同じ語 (「設計」など) を複数の段階で使うときは、段階ごとに何を決めるかを同じ箇所で並べて示す。前の章で決めると記載した事柄を、後の章で別の時期に決めると読める形で記載しない
- 仕組みの説明は、何を置くかより先に、何を防ぐための仕組みかを記載する。次へ進む基準は、道具の出力との一致ではなく、人ができる状態 (自分の言葉で説明できる など) で記載する
- 比較の表の比較軸は、特徴の章の項目と対応させる。他の手法の欄は「標準の工程で扱うか」の形で記載し、仕組みが無いと断定しない
- 抽象的な呼び名 (工程の出口 / 上流と下流 / 実装の形 / 判断の分かれる点) は、具体的な文書名や動作に置き換える (例:「工程の出口」を「各文書を作った後に確認の command を実行する」に置き換える)。規則を記載するときは例外 (後の工程で問題が見つかったら前の文書を修正する) も 1 文で添える
- 数値の基準 (行数の上限など) は、必須か目安か、他の条件とどちらを優先するかを同じ文で示す
- 表の行の見出しは、分類の記号 (「汎用 + 固有」) ではなく、確認する中身の名前 (「設計と品質」) にする。判定項目の一覧や手順の細部は載せず、定義 file を正本にする

## 2. 既存の文書を書き直すときの規則

媒体 (Notion / HTML / md / 記事) によらず、既にある文書を作り直す・短くする・一部を修正するときに従う。

- 本人が手動で編集した版があるページを作り直す・書き直すときは、その版を元にして、規則に合わせて加える内容だけを差分として書き加える。本人の版の文体 (敬体か常体か)、実際に困った事実として書かれた課題、手法に固有の仕組み (独自の表や手順) は、一般論に書き換えず維持する
- 「短く」「重要な部分だけ」と頼まれたら、先に章をまたいだ重複と、見出しや図と同じ内容の文を削る。手法に固有の仕組みを説明する節は、重複が無ければ削らない
- 社内で共有する手順や仕組みの文書には、書き手の自己評価・感想・効果の主張 (「こだわったところ」「〜しやすくなります」「手戻りが減りました」) を記載しない。仕組みが何をするかと、その目的だけを記載する。記事など個人の発信を元にするときは、該当する文を削除するか事実の文に書き換える
- 箇条書きの階層は 2 段までにする。3 階層目が必要になったら、案内の 1 文と平らな箇条書きに組み替える

- 同じ題材の資料が別の媒体にもある (Notion のページと HTML の Artifact など) ときは、章立てと中身をそろえる。片方で章を組み替えたり、事実や表現を修正したりしたら、もう片方にも同じ修正を加え、加えなかった差分は理由と一緒に報告する

### 一部を修正した後の確認

一部だけを書き換えたら、文書全体を上から読み、次の 3 点を確かめる。修正した文だけを読んで終えない。

- 言い回しを変えた主張 (基準・目的・呼び名) が、冒頭・表・比較の欄など他の箇所で古い言い回しのまま記載されていないか。見つかったら同じ言い回しにそろえる
- 節に内容を追加した後も、見出しが節の中身全体を表しているか。別の話題が入ったら、見出しを変えるか、その話題を扱う節に記載し直す
- 表に行を追加したとき、同じ内容を表の前後の地の文でも記載していないか。重なる文は削除する

## 3. 会議や定例で使う資料の構成

議題・ミーティング・打ち合わせの準備に使う資料は、媒体によらず、作り始める時点で構成を決める。本文の作成後に構成を変えると、詳細・リンク・図を追加する往復が 1 回ずつ増える。

- 先頭の章を「決めたいこと」にし、項目・推奨・決まらないときの影響を 1 行ずつの表にする
- 続けて、項目ごとの詳細 (各小見出しの先頭に結論 1 行、続けて今の状態・理由・採らなかった案・未確認の点)、想定される質問と答え、関連、の順に並べる。この種類だけは章の数の目安を超えてよい
- 本文で触れる issue・PR・コメント・PRD・code はすべてリンクにする。code は commit 固定の permalink にする
- 仕組みや攻撃・処理の流れが論点なら、図を 1 枚置く
- 件数や状態は、作成する直前に元の issue から取り直す。作成中に他の人が更新することがある
