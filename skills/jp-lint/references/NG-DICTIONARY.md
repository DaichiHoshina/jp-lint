**主体不明断定 (skill-only)**: 多くの〜 / 一般に〜 / 一般的に〜 / よく〜される / 〜と言われる / 〜だろう / 〜と考えられている

> `(skill-only)` mode は hook 抽出対象外。`/jp-lint` の見直しで、user が NG 語・用語統一の監査を明示したときだけ参照する。技術 README 等で正当な総称表現として使う場面があり、hook 自動 block / warn は誤爆コストが高いため。語源は PRINCIPLES.md `## AI臭の根本: 書き手不在` `(1) 主体を明示する`。

**主体不明断定 (warn-only)**: と言われる / と考えられている / とされている

> hook (chat 経路) が warn する grep-safe subset。上の skill-only key は「〜」placeholder 入りで literal grep に載らないため別 key として分離した。「一般的に」「だろう」は正当用法が多く誤爆コストが高いので含めない。

> 「出す」「外す」「持つ」「見る」「入れる」「切る」は意味の範囲が広く、実際の操作を読み手が文脈から復元しなければならない。実際の処理を表す動詞に置き換える: 値を出す → 返す / 生成する / 取得する / 表示する、処理を外す → 削除する / 無効化する / 分離する / 対象外にする、データを持つ → 保持する / 所有する / 格納する、チェックを入れる → 検証する / 条件を追加する、branch を切る → 作成する、PR を見る → レビューする / 確認する。日本語は語境界がなく部分一致で検査するため、「検出した」「区切って」「受け入れて」への誤爆を避けて助詞付き (を / に) の形で登録する。助詞なしの「PR 出す」は拾わないが、外向き text ではほぼ助詞を伴う (user 指摘 2026-09-06)。「外す」は助詞なしの活用形 (外す / 外して / 外した / 外さな) も対象にする (user 指示 2026-09-24)。部分一致なので `除外する` `除外して` も block される。これも禁止として扱い、「除く」「対象外にする」と書く。名詞の「除外」単独は対象外 (user 決定 2026-09-24)。
>
> 「持つ」は助詞付き 3 形では「機能を持ち、」「候補を持たない」「役割を持たせる」のような連用中止形・否定形・使役形を検出できなかったため、助詞なしの終止形と活用形 (持つ / 持って / 持った / 持たせ / 持たな / 持てる) へ広げた。連用形の「持ち」は「気持ち」「金持ち」に部分一致するので助詞付き (を持ち / も持ち / が持ち / は持ち) と「持ち方」だけを登録する。所有や属性は「保持する」「格納する」「〜がある」「〜で構成される」、責務の所在は「〜が担当する」「〜に定義する」と書く (user 指示 2026-09-17)。
>
> 「残す」も意味の範囲が広く、削除しない・書き込む・後回しにする・変更せずそのままにする、の 4 つが同じ語で書かれる。何をどうするかで書き分ける: log を残す → 記録する / 出力する、file を残す → 削除しない / 保持する、既存の記述を残す → 変更しない / そのまま使う、課題を残す → 未対応にする / 次の作業へ回す。「残る」も自動詞形として同じ扱いで、「保持される」「削除されない」「未処理のままになる」と書く。「残」1 文字は「残骸」「残高」に当たるため活用形 (残す / 残して / 残した / 残さな / 残さず / 残せ / 残る / 残って / 残った / 残らな) で登録する。「残り」「残件」「残存」は名詞として意味が定まるので対象外とする (user 指示 2026-09-17)。
>
> 「直す」は修正・訂正・置換・再実行のどれを指すかが文脈頼みになる。「修正する」「訂正する」「書き換える」「解消する」「元に戻す」と、何をどう変えるかで書く。「書き直す」「見直す」「やり直す」「取り直す」も含め、直すの複合語も同じ理由で意味が曖昧になるため対象外にせず、助詞なしの活用形 (直す / 直して / 直した / 直さな / 直せ) と自動詞形 (直る / 直って / 直った / 直らな) も登録する (user 指示 2026-09-24。2026-09-17 に設けていた複合語の除外を撤回した)。例外として「し直す」(付与し直す / 実行し直す 等) は動作の再実行を指し意味が定まるため判定から除く (user 決定 2026-09-25、`lib/jp-quality/term-extraction.sh`)。
>
> 「選ぶ」「出る」「通る」「写す」も同じ扱いにする (user 指示 2026-09-17)。「選ぶ」は判断の中身が見えない語で、「推奨を 1 つに限定する」「採用する」「該当する候補を特定する」と、何を根拠にどれを決めるかで書く。この辞書自身が「口語の圧縮動詞」の言い換え候補に「選ぶ」を並べていたので、同時に「該当するものを特定する」へ改めた。「出る」は「を出す」の自動詞形で、「error が出る」は「error が発生する」、「差分が出る」は「差分が生じる」、「log に出る」は「log へ出力される」と書く。「検出なし」へ部分一致するので否定形は助詞付き (が出な / は出な) で登録する。「通る」は「を通す」の自動詞形で、「test が通る」は「test が成功する」、「検査を通る」は「検査で拒否されない」と書く。「共通」は 1 語では当たらないため活用形で登録する。「写す」は内容を別の場所へ複製する動作で、「複製する」「転記する」「同じ内容を書く」と書く。名詞の「写し」も「規範の写し」のような言い方で使うので「の写し」を登録し、「複製」「転記した内容」と書く。
>
> 「書く」は助詞付きの形 (を書く / に書く / へ書く とその活用形) だけを登録する (user 決定 2026-09-17)。log や file への出力を指す「log を書く」は「記録する」「出力する」、「issue に書く」は「記載する」「投稿する」と、どこへ何を出すかで書く。この辞書と PRINCIPLES.md が NG 語の言い換えを示すときに使う「〜と書く」は、規範の定型として維持するため対象外にする。
>
> 「取り消す」も意味の範囲が広く、DB の行を消す・業務の操作をやめる・操作を元の状態に戻す・提案を撤回する、の 4 つが同じ語で書かれる。何をどうするかで書き分ける: `deleted_at` に日時を記録する → 論理削除する、行を消す → 削除する、発送依頼や注文をやめる → キャンセルする、与信を戻す → 与信を解除する、操作や変更を戻す → 元に戻す、提案や判断を撤回する → 撤回する、文字に付ける横線 → 打ち消し線。活用形 (取り消し / 取り消す / 取り消された / 取り消せない) と漢字だけの表記 (取消 / 取消済み) をまとめて検出するため「取り消」「取消」で登録する。法令の条文にある「取消事由」のような用語の引用と、他の人の発言の引用は書き換えない (user 指示 2026-09-24)。

**くだけた話し言葉 (block)**: やっぱ / だよ

> 「やっぱ」は「やはり」の口語短縮、「だよ」は常体の口語終助詞で、chat の敬体 (canonical: CLAUDE.md「chat は敬体」) にも外向き text の常体にもそぐわない。「やっぱ」は「やはり」に開き、「だよ」は文脈に応じて敬体 (「〜です」) か動詞終止 (「〜する」「〜ある」) に開く (user 指摘 2026-09-05)。
>
> 文末の断定「〜だ」も block する (user 指示 2026-09-12)。PRINCIPLES.md 「plain JP の文体」 が 2026-08-03 から「〜だ」で閉じないと定めていたが、検査に接続しておらず hook が検出できなかった。言い換えは動詞終止 (「〜する」「〜した」「〜ある」) か「〜になる」「〜として扱う」で、名詞述語なら「〜が対象になる」「〜を指す」のように動詞へ開く。
>
> この語は辞書の literal に登録しない。辞書の一致は fixed-string の部分一致で、「読んだ」「含んだ」のような撥音便の過去形まで一致するためこの方法を採らない。判定は構造検査 (`lib/jp-quality/structural-checks.sh` の文末断定) で行い、文末が「だ」で終わり直前が「ん」でない文だけを数える。

## 偶然一致 (false positive) 回避

hook の match logic は `grep -ioFf` (substring・case-insensitive)。技術用語 / skill 名 / library 名が NG 語を内包すると hit する (例: skill 名「robust-XX」が `robust` に hit、prose 内の `leverage` を含む製品名 / API 用語等)。

### 回避優先順位

hit した語が**地の文か、識別子か、上流 doc からの引用か**で先に分岐する。識別子でないのに backtick で囲むと、hook は検査対象外にするが読み手には NG 語がそのまま残存する。

1. **地の文の hit (default)**: 検出語を含む**文を単位に書き直す**。語だけを別の語へ差し替えると、同じ問題が別の語形で残り、前後の係り受けが壊れる。置換候補は書き直しの方向を示すもので、そのまま貼り替える対象ではない。
   - 例: `本機能は効率的に処理を行うことができます` → ✗ 語だけ差し替えた `本機能は効率よく処理をします` / ○ 文ごと書き直した `1 件あたり 200ms で処理する`
2. **識別子の hit**: 技術用語 / command 名 / 固有名詞は backtick で囲む。`_strip_code_blocks` が ` `code` ` / ` ```block``` ` を除去するため hook をすり抜ける。commit message / PR / Slack / Notion / DD / RCA すべて適用。囲ってよいのは、その語が識別子として画面や command に現れる場合だけにする。
   - 例: `leverage を使う` → ✗ block / `` `leverage` ライブラリを使う `` → ○ pass
3. **上流 doc からの引用**: Design Doc の受け入れ条件のように上流 doc の文言を転記する箇所も、backtick で装飾しない (装飾が並ぶと読み手はどこが大事か判別できない。user 決定で辞書の照合より装飾なしを優先する)。NG 語を含まない原文はそのまま地の文で書く。NG 語を含む原文は、上流 doc を修正できるならそちらを修正してから引用し、修正できないなら NG 語の無い表現に言い換え、言い換えたことを chat で user に 1 行伝える
   - 例: 作業計画書の完了条件が Design Doc の受け入れ条件 `取得が残っていない` を指す → ✗ backtick で囲んで原文のまま / ○ `取得が削除されている` と言い換えて地の文で書く
4. **whitelist 追加 (incident base 限定)**: 1, 2 で対応できず**かつ同じ語で 3 回以上 false positive 実害**が発生した時のみ、本 file に whitelist section を新設して exact match 除外する。先回り whitelist 化禁止 (hook 機能後退の温床)。

### canonical 運用

- skill 名 / agent 名 / library 名 / API method 名 を**外向き prose に bare 出現させない**。code fence 内に閉じ込めるか日本語説明に置換する
- block 発生時の retry は本 section の優先順位に従う (whitelist 提案を先に出さない)
